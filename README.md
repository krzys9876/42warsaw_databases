# Why databases

Whatever code you write, at some point you must store and read the data your application uses. It may be a small set of configuration options, it may be bilions of rows. Over more than sixty years the industry have developed various pieces of software that try to solve this challenge - they all fall in to the database category.

You may treat them as simple black boxes or dive deep into their internals. You will often browse the large catalog of existing databases, you might event want to develop your own one. 

Whatever your project is there is no easy way out. People love or hate databases but every programmer at some point must learn to live with them. 

## The history

The history of technology not only teaches us about our great predecessors. It also shows that so many of the so called _modern_ solutions have been studied or solved long ago, we just don't want to admit it. It also explains why things are what they are, why we use this language, framework or architecture not the other.

It is also fun. Go and read IT history books and articles, watch films and enjoy.

## SQL

This is the one obvious think that you cannot ignore as IT professional. Regardless which camp you're in : _SQL is great_ or _SQL is old and boring_ there is no easy escape. It is also very simple in its fundamentals so it is not worth skipping it. Instead, sacrifice a few afternoons, get some understanding and it will stay with you forever, like swimming or riding a bike.

## NoSQL?

The NoSQL (Not Only SQL) is the answer to obvious limitations of traditional relational databases. People struggle with schema limitations, large data sets, hardware or specific query requirements that SQL does not (or did not) provide. Hence solutions like MongoDB or Apache Spark got traction. 

Some of these limitations are now built-in into the mainstream databases. Regardless if you face these kind of limitations, it is important to know that there is always a place for new ideas.

## How to escape SQL?

Programmers in general hate SQL (for no good reason, imho). There are tools that isolate their sensitive minds from SQL and let them pretend it is not there. In object oriented languages, like Java, they fall into the ORM category (_Object Relational Mapping_). Using your favourite programing language you may describe the objects in such a way that the tool will handle all the work for you.

Is it a remedy to all the problems? Certainly not, as always it comes with the cost. Is it worth knowing and using. Certainly yes.

## In practice

Just like with the code, knowing the syntax, algorithms and build tools is not the same as working in a production environment with million-row codebase, in databases knowing SQL is not the same as handling hundreds of terabytes of data. You will see how it works at scale.
